# Material shader startup and cache contract

Updated 2026-10-26. This describes the implemented editor path, the relevant UE 5.8 source findings and the measured cache workload. It is not a full editor startup or gameplay FPS benchmark.

The current native material format is v6 with graph schema 20 (readers accept schemas 1–20), material ABI 40, twelve graph texture slots and 208 vec4 parameter rows. `renderer-manifest.json` records the maintained bgfx port 17/API 130 and view layout 5. Generated fragments, node previews and native domains have separate entries in canonical `MaterialGraphSourceRevisions.h`; all entries currently retain revision 42. That common value preserves existing artifacts, not a global invalidation rule. Source revisions, host recipe contracts and actual dependency contents jointly identify each affected stage. Historical generator/ABI numbers and workload measurements below describe their original checkpoints.

## Presentation and ownership

`MaterialGraphPrograms` first tries the optimized persistent stages through `ShaderCacheReadSession`. The cache key includes generated source, compiler contents, build/recipe contract, optimization policy and discovered dependency contents. All required stages pass structure, reflection, ABI and DXBC preflight before a coherent GPU generation publishes. A valid warm bundle does not invoke shaderc or wait for a resource worker. Unchanged requests reuse the in-memory generation. A partial hit retains each valid vertex/fragment pair and requests only missing work; cache snapshot validation prevents mixing results from different source epochs.

Both fixed and generated shader binaries use the same atomic cache publisher as their dependency/recipe metadata. A matching immutable file is retained; a competing publication is accepted only when its bytes match. The existing Windows publisher retries transient access/sharing/lock failures for at most 500 ms without deleting the destination, and reports the path and Windows error on persistent failure. A failed rename no longer treats an arbitrary existing regular file as a valid compiled artifact. Compiler staging files are cleaned on success, cancellation and publication failure. This changes publication reliability without changing cache identities or shader optimization policy.

Direct3D 12 is the default runtime backend; Direct3D 11 remains selectable in application Preferences or through the nonpersistent `--renderer dx11|dx12` launch override. Both backends consume the same Windows Shader Model 5 / DXBC binaries through the pinned bgfx implementation. Engine embedding, generated materials, hot reload and the CPU-only preparation commandlet retain one shared compiler/cache family. The existing `dx11` token in `ShaderCompileConfig::buildContract` identifies that established compilation family; it does not restrict runtime selection to DX11. Changing only the runtime backend does not invalidate the source baseline or trigger shader compilation. New source, topology, compiler or ABI changes still do. DXBC reflection and all binding, output-target and compute-group checks remain enabled for both backends. Vulkan/SPIR-V compilation and validation remain unimplemented for this rich generated-material path. The shared renderer's modeling recipe has its own SPIR-V shader family; that does not establish rich Forward+/PBR Vulkan support.

A true runtime miss compiles expensive Model/Particle/Decal surface, transmission and reflection fragments, and eligible native domains, on the existing ResourceManager workers with the shared interactive policy in `MaterialGraphCompilePolicy.h`; cheap coverage and vertex stages retain full optimization. Omitting shaderc's `-O` sets `D3DCOMPILE_SKIP_OPTIMIZATION`; `-O 0` still selects an FXC optimization level. After 750 ms of quiet, background work prepares the full O3 replacement. A new foreground miss cancels obsolete background optimization; sibling owners share pending optimization work. Background admission permits one generated O3 stage at a time across those owners, leaving another existing worker available for model and image loading. The permit remains held until the one-shot resource loader finishes and publishes, including failure or cancellation; the complete optimized packet still publishes atomically after all its required stages pass preflight. The two optimization policies have distinct cache identities. Release preparation first prepares usable programs for the complete valid catalog, then prepares missing O3 results. Scene/Game rendering continues; there is no whole-world preparing-materials gate. Existing prepared graph entries retain their last complete packet, including programs, uniforms, textures, coverage and render state, until a coherent replacement is ready. Failed compilation retains that packet and reports the diagnostic. The first usable shader is temporary: full optimization replaces it atomically, with no authored-material changes.

Runtime program demand is separate from shader generation. `MaterialGraphUsage::Surface` requires Model, Picking, PointShadow, Particle and DirectionalShadow, together with both transmission programs when the material enables refraction. It omits the optional ModelReflection/ParticleReflection pair. `SurfaceReflection` requests that pair while returning a ready surface generation as `current=true` until the complete extended generation is available. Optional SSR compilation or failure does not mark a valid base material as graph-pending or hide its model. SSR uses its environment fallback while its material reflection pair is unavailable. Submitted packets pin their original generation throughout the upgrade.

Opaque SSR captures exact FP32 receiver position, shading normal/roughness and geometric plane before one shared `cs_ssr_trace` compute dispatch traces the current unfogged opaque source. The compute split retained the then-current ABI39/source41 interface; current source revisions are recorded above. It separates ray traversal from opaque material evaluation while preserving ray quality and current-frame source ownership. Reflection material fragments retain inline tracing for Alpha/glass and runtime-faded opaque/masked meshes; the split does not establish a reduction in first-time material compilation cost. `cs_ssr_trace` participates in the named engine-program registry, embedded publication, runtime source baseline and atomic hot reload alongside `cs_ssr_reconstruct`. Included-source changes still invalidate dependent generated reflection stages, and genuinely changed stages still require compilation.

`AssetLibrary::ReflectionDemandScope` derives this demand from the preparing view's effective Environment SSR setting: enabled with positive strength. Scene/Game preparation, scene particles, material previews and thumbnails establish their own nested scopes; ordinary preparation defaults to the surface family. Node previews retain their one-program contract. `MaterialGraphUsage::Complete` remains the default direct request for explicit full-family callers and tests. Usage changes only the host's admitted bundle; generated IR, per-stage recipe names, compiler policy identities and persistent cache entries are unchanged. Runtime source/ABI invalidation and last-good publication rules still apply to both families.

Individual stage names derive from their own generated source rather than the complete material topology key. Coverage has an independent postorder traversal and the first uniform/sampler slots. Surface-only graph rewiring therefore cannot rename or move unchanged coverage. Depth source contains only the expressions consumed by that pass: Mask opacity for shadows, Mask or transparent opacity for picking. Identical compiler inputs share an artifact; PointShadow additionally consumes the prior-world varying and emits the optional motion MRT, so its interface differs from DirectionalShadow. The complete material retains a whole-bundle identity for coherent publication. Material and node-preview owners share their cache read session and source-family dependency memo.

`materialGraphFixedSurface` certifies an exact subset for the embedded model program. It accepts opaque standard PBR with conventional color, ORM, normal, AO and emission slots, uniform factors/arithmetic and compatible shared mapping. Texture roles, channels and samplers must match. Normal UV must also match each primitive's tangent UV, except the built-in box's equivalent sets. Certified model graphs use that program as their complete renderer: no generated source is built and no shader jobs are queued. Normal texture streaming keeps its demand, priority and resource leases. These packets are complete rather than graph-pending, and a topology change outside the certified subset selects the ordinary generated-program path.

This is deliberately separate from `materialGraphLegacySurface`, which is compatibility/Inspector transport and can approximate unsupported graph expressions. The certified path rejects independent coverage, animated expressions, textured Power/Add/Lerp, incompatible packed channels, different transforms and other unsupported branches. Those use the domain fallback until their generated program is ready, or retain a previous coherent model packet. Particle and node-preview behavior is not inferred from the fixed model slots. No authored graph, factor, assignment or image is rewritten by presentation.

Scalar/color values, texture identities, sampler settings and UV transforms are parameter data when graph topology stays compatible. They do not require a new shader permutation. Renderer ABI/source changes and actual topology changes can require compilation; persistent cache reuse cannot remove a genuine first compilation of different code.

Grunge is a generated texture source within this same publication contract. ResourceManager workers synthesize one content-keyed canonical 1024×1024 linear RGBA8 image and its data mips; AssetLibrary's TextureStreamer publishes and leases the GPU allocations on the main thread. Runtime material sampling and the node's embedded/explicit flat 2D previews derive from the same pixels; Value previews display raw numerical grayscale, while RGB previews use sRGB display copies. Independent dirt specks, stains, scratches and leaks opacity controls combine those layers with noise in a single image, sampled through one of the shared twelve Texture 2D/Grunge slots. Changing Seed, noise controls or Layers regenerates image data asynchronously while keeping compatible programs and the last complete material/image visible. Tiling and Mapping only change sampling, without rebaking the canonical image. Adding or rewiring a node can still require its first generated shader compilation.

The generated-image key includes generation settings, resolution and generator revision; bump that revision when pixel equations change. Settings live in graph schema 20 within native material v6 (Grunge was introduced in schema8), with graph schemas 1–20 readable and older Grunge style settings converted to explicit layer values on load. The current representation stores Stains Opacity and Leaks Opacity alongside the other independent layers and writes no Style field. Grunge needs no external input bitmap and creates no separate Asset Browser entry or authored image file. Its layered controls are informed by the readable local Adobe `grunge_concrete.sbs` graph; Crimson's generator is independent and does not claim identical pixels. Shader cache preparation and generated-image preparation are separate work: a warm shader cache does not certify that a requested Grunge image is already resident.

## Diagnosing missing materials or browser cards

Follow the owner of the pending result before changing scheduling or invalidation. A complete shader cache does not certify decoded images, generated pixels, streamed mips, a prepared preview mesh or a completed thumbnail readback.

| Result being prepared | Entry points and evidence |
| --- | --- |
| Committed graph and referenced source materials | `AssetLibrary::graphCache`, `findMaterial`, `modelMaterialsDiagnostic`; missing or incompatible Blend children are definition/dependency failures, independent of shader optimization. |
| Usable compiled programs | `MaterialGraphPrograms`, `MaterialGraphCompilePolicy.h`, `ShaderCompiler.cpp`; distinguish a current Interactive packet, optional O3/reflection work, a true cold miss and a failed generation retaining its last-good packet. |
| Cached or procedural image pixels | `AssetLibrary::preparedResizeTexture`, `materialNodeImagePreview`, `grungePreview` and `TextureStreamer::requestGenerated`; content recipes, source fingerprints and worker publication govern these results. Compatible image edits can regenerate pixels without changing shader topology. |
| GPU texture residency | `TextureStreamer`, `AssetLibrary::preparedGraphBindings` and `modelBindings`; inspect `graphPending`, `complete`, `sourceReady`, diagnostic and exact source fingerprints. Shader readiness and image decoding alone do not prove required mips are resident. |
| Browser image and retained preview geometry | `AssetPreviews::diagnostic(id)`, `AssetPreviewStats`, `AssetPreviewCache.cpp`, `EditorResources` and `Renderer::pollThumbnail`; trace source planning, persistent descriptor validation, bindings, mesh streaming, render submission and readback separately. |

For a reported recurrence:

1. Preserve the paired executable/shader-tools identity, material ID, source changes, relevant preparation report and compiler process evidence before deleting derived caches. Check report timestamps: `build/Release/material-cache-preparation.json` is overwritten by later completed runs, so an older warm report cannot certify an unfinished new build. Record `presentationTopologies`, `presentationFailures`, `presentationMs`, final failures and compiler invocations separately. The first-use timer includes catalog discovery and preparation; it does not measure a rendered scene.
2. Read the card's actual preparation stage and binding diagnostic. Generated shader compilation, generated-image work, texture streaming and thumbnail rendering require different fixes. Cached-image/procedural bindings can intentionally carry generated-content fingerprints rather than original-file fingerprints; do not force them through an external-image equality check. Direct file-backed sources must still match the exact rendered source version.
3. Keep preview mesh retention inside the ordinary frame lifetime: `EditorResources::beginFrame`, `AssetPreviews::pump`/`retainExternalModelForFrame`, then `EditorResources::endFrame`. An unretained shared preview mesh can lose streaming ownership between retries. A selected Vertex Paint tool or hover preparation is not an active paint stroke; browser pumping pauses only for the transient active stroke and resumes immediately when it ends. Do not reintroduce a document/UI command gate to wait for thumbnails.
4. Reproduce with the actual resource and renderer owners. Require authored pixels and source versions, then destroy the preview owner, evict GPU cards and require persistent restoration without rendering. A valid GPU handle, a scheduler unit test or successful shader syntax alone cannot establish that the correct material appeared.
5. Separate stable warm reuse from deliberate first use. A warm run must use unchanged compiler/source/recipe inputs and report zero compiler processes. A cold run belongs in disposable storage; record whether it waits for the first usable packet or final O3. Concurrent editor/warmer requests for the same stable input must share compilation without blocking main-thread cache-only lookup.

The Spot-light interface uses material ABI40: local records grow to eight texels with reflected `u_clusterRecordLayoutV8`, and lit fragments consume the three sixteen-entry projective shadow arrays. The fragment/node-preview/domain source revisions remain42 because generated expression text is unchanged; real shared-include dependencies and affected Model/Particle recipe identity invalidate their actual consumers. Independent coverage, Decal, reflection/transmission and domain recipe literals retain their existing identity; changed included-source contents still invalidate every actual consumer. A recipe's historical `abi39` text is not the current renderer family manifest. Preflight always validates the current pass interface.

## Startup and browser regression requirements

These are implementation requirements, not optional performance advice. Preserve them when changing material generation, shader compilation, previews or build preparation:

- Canonical `MaterialGraphSourceRevisions.h` owns explicit fragment, node-preview and native-domain revisions. Change only entries whose emitted program input changes. A Decal-only change must not rename Model, coverage, Particle, node-preview or domain stages. Host surface and Decal recipe contracts are separate; the historical `decal-domain-v2` text retained in the surface contract is part of its existing identity, not permission to bump it for a new decal feature. Profiling records a diagnostic maximum of the table, which must never become a global compiler-input salt. Shared shader or ABI changes still invalidate their actual consumers; do not suppress content, compiler, dependency or preflight validation to obtain cache hits.
- The build warmer prepares the complete usable catalog before optimizing any cold expensive surface/domain program. It uses the same `MaterialGraphCompilePolicy.h` as runtime. Valid Full pairs win; otherwise each required Interactive fragment/domain pair must be complete and preflighted. All materials receive that first-use pass before the second O3 pass begins. Cache maps distinguish optimization policy and coalesce actual stages. Warm preparation must retain zero compiler processes and one cache read per shared stage. `presentationTopologies`, `presentationFailures` and `presentationMs` describe the first pass separately from final optimized preparation.
- The editor, warmer and sibling workers share a cancellable per-input `ShaderCompileLease` in the compiling path: ResourceManager workers or the CPU-only preparation utility. After acquiring it, a waiter recomputes dependencies and checks the published artifact. Concurrent requests for the same stable input share its compilation; unrelated inputs can compile concurrently. `ShaderCacheReadSession`/presentation-thread cache-only lookup never acquires or waits on this lease. Newly discovered dependencies can still require the validation compile described below. Compiler staging names remain process-unique, publication stays atomic, and canceled or failed requests must release ownership without damaging another caller's complete artifact.
- A usable Interactive generation is current. Do not require `optimized == true` to display a material, model or thumbnail. Optional reflection/optimization work cannot hide ready surfaces. Retain a complete last-good packet, including textures, uniforms, coverage and render state, until its coherent replacement is ready. Never gate the entire scene or editor commands on one material's readiness.
- Preview descriptor deduplication and GPU source-fingerprint lookup must use the same absolute Windows-case-insensitive `resourcePathKey` identity. Comparing raw relative/absolute or case-sensitive path spellings can leave a valid texture pending forever. Preserve exact source-version checks: an alias of the same unchanged file is accepted; a changed fingerprint or different file is rejected. Pending cards must allow ready siblings to progress. Read-only per-card preparation diagnostics must identify a genuine pending stage.
- Complete the Release wrapper, including shader-cache preparation, before handing off a build. A linked executable alone does not establish a prepared project cache. Use the paired staged shader/include/compiler family; do not compare or combine results from a different executable or source generation.

## Per-mesh shading interface

The ABI/generator32 mesh-shading checkpoint introduced `u_meshShading` and a separate `TEXCOORD5` normal input. The primary vertex/cache layout remains 108 bytes. Ordinary modes bind a zero-copy alias of its original normal; Smooth binds an optional 12-byte-per-vertex stream. Native tessellation control points keep displacement and shading normals separate. The generated domain reconstructs Smooth height normals without changing the selected geometry or material texture bindings. The domain contract includes `shading-stream1-texcoord5`; generated shader/cache identities include `mesh-shading-v1`, preventing older families from being reused.

The embedded and hot-reload program family includes `cs_model_smooth_normals`, which computes animated Smooth normals after deformation. Shader preflight, compiler recipes, atomic reload and source-baseline staging publish it with the same executable family. Mesh shading is per occurrence and does not add a material graph schema or material-file migration.

## Blend source and paint contracts

Graph schema20 introduced per-reference height blending and local layer controls at generated source41, retaining ABI39. Referenced or explicitly overridden Height is a surface shading signal independent of hardware displacement. Disabled height layers omit otherwise unused height samples; active height, local tint/roughness/channel controls and explicit mapping overrides follow the same immutable source resolution, preview, thumbnail and commandlet preparation path. Numeric controls update parameter packets without recompiling compatible code. Height-enable and mapping-structure changes may compile a new topology. Existing paint RGB, subdivision and one-stroke document history remain unchanged. The ready example reuses the existing aligned stone-floor and noise height maps and keeps its original material identity.

The source40/ABI39 paint checkpoint introduced a dedicated paint vertex shader and auxiliary stream while retaining the primary 108-byte layout, twelve graph texture slots and 208 parameter rows. The paint varying family carries inverse-bilinear quad coordinates and RGB weights; it adds no sampler. Ordinary opaque picking and shadow variants use the same derived CPU geometry. Mesh Blend participants omit instancing and request original LOD0. A mesh without authored RGB binds a zero paint stream and renders Base. The embedded paint VS, manifests, stage recipes, source baseline, preflight and hot reload remain coherent.

Graph schema19 introduces Material Reference and the four typed Surface layer pins. `resolveMaterialGraphSourcesData` accepts immutable committed native source snapshots, validates direct Lit/Opaque compatibility, expands only active references and retains cached-image provenance. Source tessellation contributes its surface and optional Height without enabling geometric displacement on the Blend. Source semantic signatures invalidate parent packets and thumbnail dependencies. Value-only child edits reuse shader topology; changed child topology compiles affected generated stages. Parent and node previews resolve the same sources, including a detached Surface preview. The project material-cache commandlet loads child sources before generating each parent family, so a new Blend asset can be prepared before the editor opens it. Expanded graphs share the ordinary sampler/row limits and retain the existing coherent last-good publication rules.

`AssetLibrary::graphCache` first checks the immutable graph owner. Ordinary graphs without active Material References reuse their entry directly. Blend entries retain the authored active reference IDs and committed source snapshots/revisions; hits refresh dependency demand and compare those identities without copying, ordering or validating graph nodes. Source changes, missing/restored assets and reference replacements rebuild the entry through the same compatibility checks. The `Material graph cache rebuild` CPU zone covers that miss path. Shader and material ABI/cache identities are unchanged.

## Material catalog startup

Model manifests with explicit shared-material IDs do not need background material metadata loads just to rediscover native assets. Native catalog scanning already discovers those assets. Implicit imported material slots and explicit references to a package's own imported sidecars still run migration. A promotion callback records only files actually created; resource publication refreshes the material catalog once when new/discovered sidecars require it. Unchanged model completions do not repeatedly load and serialize every native material. External material notifications still refresh their source.

The inspected project contained 121 model manifests, with 120 explicitly referencing shared native materials. The previous path queued metadata for all of them and rescanned the complete native material library after each completion. This work is independent of shader cache hits and could recur on every launch.

## Embedded engine programs and build preparation

The canonical renderer submodule owns shader sources, compilation commands and
embedded headers. `Crimson::HostShaders` exports the generated interface to
Engine adapters and tests; canonical headers precede the Engine's host-generated
resource directory so stale local shader headers cannot satisfy these includes.
Runtime shader tools stage the same canonical sources and compiler family.

The executable already contains its engine shaders. `ShaderReloadSession` compares the selected runtime source/include/compiler family against a build-generated SHA256 baseline before requesting any engine jobs. Equal bytes reuse embedded programs even after timestamp-only staging or relocation. No engine shader compilation or duplicate program publication is queued. The file watcher retains its dependency baseline; actual edits use the existing coherent hot-reload path. Debug source edits made before launch also differ from the embedded baseline and therefore still reload. The baseline lives in the executable rather than in a mutable sidecar that could falsely certify different source bytes.

`Build.cmd Release` runs the CPU-only `crimson-material-cache` utility after the executable and paired `shader-tools` payload have been staged. It scans native material assets and the two protected defaults, coalesces equal graph topologies, compiles each missing shared vertex only once, and prepares complete material families: the five required passes, both transmission variants when refraction is enabled, and both reflection variants for eligible Lit materials. Decal graphs prepare their separate Decal pass. It preflights them against the build's embedded vertex interface and current generated manifest. The complete valid catalog receives its first-use pass before missing O3 surface/domain work begins. Runtime lazy reflection does not narrow this build-time demand: preparation includes optional SSR variants even when the current scene has SSR disabled. For an initialized project with its protected defaults present, derived output stays below `.crimson/cache/shaders`; existing materials, textures, scenes and layout remain authored inputs. Bootstrap can initialize content storage or materialize missing protected defaults. The normal build report is `build/Release/material-cache-preparation.json`.

This preparation pays the cost of genuinely changed custom shader code during the explicit engine build, rather than the user's next editor launch. Repeated builds reuse content-addressed artifacts. It does not reuse old code across a changed renderer interface or approximate the character's independent roughness-texture expression. The active character material in the 2026-10-16 fixture requires generated shaders; Quader color-texture materials and the ordinary default qualify for the embedded model program. Opening an external project or creating a new unsupported graph topology can still require first compilation at runtime, with the existing asynchronous/last-good behavior.

## Avoiding redundant validation

`compileShader` owns the exact content identity and cold-compilation before/after content validation. Its ResourceManager wrappers use file-state guards around the loader rather than hashing all inputs again on both sides. Named shader compilation reuses its initial fingerprint instead of immediately repeating it. Warm reads check file states before and after content-key lookup. Main-thread cache sessions share content-hash prefixes across bundles and check that the observed source epoch remains coherent before publication.

Shaderc's dependency output can remove inactive lexical includes. A strict subset does not require another compiler process. A newly discovered macro include does require another validation compilation against the expanded content identity. Tests cover both cases, changed compiler/source/contract, malformed binaries, multi-pass coherence, failure recovery and retirement.

Do not replace content-addressed shader identity with timestamps, ignore the compiler version, reuse a partially valid pass family or run bgfx from a worker. Release must use the shader/include family staged with its executable; a live checkout with a different uniform ABI must never become its fallback source.
